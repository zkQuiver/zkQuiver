Why

the problem this solves

The trust gap in Robinhood Chain

Robinhood Chain is a Layer 2 built on the Arbitrum stack. Its security story is the optimistic-rollup one: state roots are posted to Ethereum, and if a posted root is wrong, a validator submits a fraud proof and the bad root is rejected. The catch is in who may do that. Today the fraud-proof system is not permissionless, only whitelisted validators can dispute a state root, and there is no forced-inclusion path if the sequencer censors a transaction. In practice, users trust a small permissioned set to keep the state honest.

That is not a criticism unique to Robinhood Chain, most young rollups launch this way, but it is a real, explicit trust assumption. Call it the trust tax: the gap between "the chain is honest" and "I can check that the chain is honest."

What anchoring does about it

zkQuiver narrows that gap with an independent, append-only record of the chain's state history. For every contiguous window of blocks, a record is anchored on-chain committing to the state before and after the window. The anchoring rules make the record chain rigid: records arrive in strict sequence, windows must tile perfectly with no gaps or overlaps, each proof hash can be anchored exactly once, and every record is signed over a message bound to this exact chain, contract, window, and sequence position. The result is an unbroken lineage from block 1 that anyone, not just whitelisted validators, can audit.

Today, the integrity of what's inside each record rests on the aggregator signature (see Security model). Phase 3 replaces that trust with zero-knowledge proofs verified on-chain. The anchoring skeleton is built to receive them.

Concepts

the vocabulary, precisely
TermMeaning
block windowA contiguous, inclusive range of blocks, at most 2048 long. Windows tile the chain perfectly: the first starts at block 1, and each next window starts exactly where the previous ended plus one.
artifactA small JSON document committing to one window: its bounds and the state roots before and after. The unit the prover hashes and signs over.
proof_hashblake3(canonical_json(artifact)), a 32-byte fingerprint of the artifact. Anchorable exactly once.
DS messageThe 98-byte domain-separated message the aggregator actually signs. Binds proof_hash to chain ID, contract address, window bounds, and sequence number, so a signature is useless anywhere but its exact context.
ds_hashkeccak256(DS message), signed EIP-191. The contract recomputes it independently and recovers the signer with ecrecover.
seqStrictly monotonic record counter starting at 1. A signature over seq N cannot anchor at seq N+1, replay across positions dies with the hash.
aggregatorThe key that signs DS messages. Rotatable with zero downtime: a successor key becomes valid from a scheduled sequence number onward.
Validator LockERC-20 escrow operators stake to register as provers. Accepted proofs accrue to their on-chain counter, the hook for Phase 4 rewards and slashing.
ProofRecordThe immutable on-chain record: hashes, state roots, window, submitter, timestamp, and whether a ZK verifier accepted it.
commitment levelHow final a record's transaction is: 0 included (latest) → 1 safe (safe) → 2 finalized (Ethereum L1 finality of the containing batch).

Spec

bytes, rules, and a worked example

Canonical JSON

Three independent implementations (Solidity-adjacent tooling, TypeScript, Rust) must hash identical bytes, so artifacts are canonicalized with strict rules: object keys sorted lexicographically, no whitespace, lowercase hex, integers only, no scientific notation.

canonicalization, same input, one output
// input (any key order, any spacing)
{ "start_block": 1, "artifact_id": "550e…", "end_block": 64,
  "state_root_after": "000…002", "state_root_before": "000…001" }

// canonical form (this exact string is what gets hashed)
{"artifact_id":"550e…","end_block":64,"start_block":1,"state_root_after":"000…002","state_root_before":"000…001"}

// proof_hash = blake3(canonical_bytes)

The 98-byte DS message

The aggregator never signs a bare hash. It signs this exact structure:

prefix14 B ascii
chainId8 B u64
contract20 B addr
proofHash32 B blake3
start8 B u64
end8 B u64
seq8 B u64

prefix is the ASCII bytes "zkRH/anchor/v1" · all integers big-endian · total exactly 98 bytes

computeDsHash: the on-chain half of conformance
function computeDsHash(bytes32 proofHash, uint64 startBlock,
                       uint64 endBlock, uint64 seq)
    public view returns (bytes32) {
    return keccak256(abi.encodePacked(
        DS_PREFIX,               // "zkRH/anchor/v1", 14 bytes
        uint64(block.chainid),
        address(this),
        proofHash, startBlock, endBlock, seq));
}
escrow in, escrow out
function registerValidator() external {
    // status → Active, then pull exactly lockAmount of lockToken
    lockToken.safeTransferFrom(msg.sender, address(this), lockAmount);
}
function unlockValidator() external {
    // status → Unlocked, escrow returned in full
    lockToken.safeTransfer(msg.sender, lockAmount);
}

API

orchestrator reference

All mutating endpoints require an Idempotency-Key header: retrying with the same key returns the original result instead of double-submitting.

POST /artifact: validate, canonicalize, store
curl -X POST localhost:8080/artifact -H 'Idempotency-Key: p1' \
  -H 'Content-Type: application/json' -d '{
    "start_block": 1, "end_block": 64,
    "state_root_before": "000…001", "state_root_after": "000…002" }'

201 → { "artifact_id": "550e8400-…", "proof_hash": "ab12…",
        "status": "canonicalized", "file_path": ".../550e8400-….json" }
POST /anchor: sign the DS message, submit on-chain
curl -X POST localhost:8080/anchor -H 'Idempotency-Key: a1' \
  -H 'Content-Type: application/json' -d '{ "artifact_id": "550e8400-…" }'

200 → { "txid": "0x9c…", "seq": 1, "ds_hash": "8e4a…",
        "status": "anchored", "block_number": 1234567 }

Before submitting, the orchestrator recomputes ds_hash locally and calls the contract's computeDsHash view; on any mismatch it refuses to submit. Implementation drift fails closed. GET /proof/:artifact_id returns the artifact plus its hash; GET /health reports service status.

Security

what is guaranteed, and by what

Guaranteed today, cryptographically

Anyone can verify, from public data alone, that the anchored record chain is well-formed: every record correctly signed over its full context, sequence unbroken, windows tiling perfectly, no proof hash reused. Replay of a signature across chains, contracts, windows, or sequence positions is impossible, the DS binding makes each signature single-purpose.

Trusted today, replaced in Phase 3

The truth of the state roots inside a record currently rests on the aggregator key: the contract proves who signed, not that the state transition is correct. The IProofVerifier slot exists exactly to retire that trust, once an SP1/RISC Zero adapter is set, each record must carry a proof that the claimed transition holds, checked on-chain. Until then, honest framing is: signed hash-anchoring with ZK-ready rails.

Key compromise & response

If the aggregator key leaks, an attacker still cannot rewrite history (records are immutable, hashes unique) or skip ahead (sequence is strict), they could only extend the chain with bad-but-well-formed records. Response: setPaused(true) halts anchoring; scheduleAggregatorRotation(next, activationSeq) hands over to a new key from a chosen sequence number, with no downtime in the honest case.

FAQ

asked, answered plainly

Is zkQuiver zero-knowledge today?

No. Today it is a hash-anchoring protocol with a pluggable slot for on-chain ZK verification (Phase 3). Every page of this site says so, because a verification project that overclaims verifies nothing.

Why do the contract files end in .sol, isn't that Solana?

.sol is Solidity, the language of Ethereum and every EVM chain, including Robinhood Chain. Solana is unrelated: its programs are Rust (.rs). Seeing .sol here is exactly what confirms this codebase targets an EVM chain.

What does the verify button on the overview page actually run?

A 17-assertion cryptographic conformance suite, executing locally in your browser: keccak-256 against universal known-answer vectors, canonical-JSON determinism, every byte offset of the 98-byte DS message, and the replay-binding properties. It does not touch a chain, there is nothing deployed yet. From Phase 2, it gains an on-chain step: cross-checking the browser's DS hash against the deployed contract's computeDsHash over RPC.

What funds the proving?

The zkQuiver token carries a 3% buy/sell tax routed to the prover treasury, which pays for zkVM proving compute, anchoring gas, and infrastructure. Until the ZK layer ships, the treasury accrues toward proving infrastructure; the treasury address and flows will be published on-chain.

Can I run all of this myself?

Yes, that's the point. node orchestrator/src/kats.js needs nothing installed and runs the same 17 assertions as the website. npm install && npx hardhat test exercises the full contract lifecycle on an in-memory chain. The repo's CI runs both on every commit.
